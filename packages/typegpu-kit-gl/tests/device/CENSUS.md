# Census of readbacks, uploads and CPU kernels

What each example costs the WebGL fallback per frame in transfers between GL and the CPU, measured on 25 November 2026 in headless Chromium on ANGLE over Metal, at `webgl-kit-fallback` 19c8d837. To regenerate it, serve the docs (`npx astro dev --port 4460` in `apps/typegpu-kit-docs`) and run `node packages/typegpu-kit-gl/scripts/examples.ts --base http://localhost:4460 --stats --out <dir>`. Each example loads with `?backend=webgl&stats`, which exposes `webgl.statsOf(root)` to the script; it runs three seconds once ready, then the script takes the difference of the device's stats 120 frames apart. The script prints a table sorted by readback time and writes `<dir>/report.json`, which also lists every kernel, read and upload per frame. Two runs on a machine shared with other agents' tests give the two figures in each cell, `run 1 / run 2`.

Counts and bytes are stable across runs. Readback milliseconds are not: a read is a synchronous `readPixels`, which waits for all GPU work queued before it, every other page's in the browser included, so it measures the GPU's load more than the read. Stampede's culling read 11.7 ms a frame in one run and 52 ms in the other. Kernels that take fixed steps at 60 Hz run every other frame at 120 frames a second, so their counts per frame are halves. CPU kernel milliseconds include the readbacks those kernels caused, since a CPU kernel reads a buffer back when it binds it.

Two rows have changed since, measured the same way at aef62e49. `night-market` reads nothing back: `dof` no longer copies its moved focus into its settings where compute runs on the CPU, so finding 2 below is settled. `ocean` draws its mips and packed maps in render passes and makes 12 GPU-form dispatches a frame where it made 39. The other rows read as they did.

## Findings, costliest first

**stampede** (known): reads 11.7 to 52 ms and uploads 610 KB a frame. This is the culling that LIMITATIONS's "Device" section describes, in six cull passes a frame. `cullFlagging` flags rows on the GPU, and `cullWalking` lists them on the CPU, reading each pass's `flags` back (262 KB the largest). It runs there because it writes `culledBuffer` whole, which is larger than 1024 bytes. GL then uploads each `culledBuffer` it wrote, 525 KB a frame from the largest. The upload is not in LIMITATIONS.

**night-market** (new): waits 5.8 to 9.8 ms a frame on a 24-byte read. `dof.create` with `pull` (`PULL = 5`) runs its focus kernel `moving` every frame (`packages/typegpu-kit/src/post/dof.ts`, `move`). Its GPU form writes the `state` buffer (`Focus`). `record` then copies `state.focus` into the settings uniform with `copyBufferToBuffer`, and the device's `copyBuffer` (`src/device/encoder.ts`) calls `source.sync()`, which reads `state` back and waits for every pass queued before it: shadows, the scene and TAA. No CPU kernel is involved, so placement has nothing to move. `moving` reads the depth texture, so moving it to the CPU would wait just as long. hex-isle also uses `dof`, but without `pull`, so it never runs the kernel and pays nothing.

**forest** (known): waits 2.2 to 9.1 ms and uploads 56 KB a frame. This is the culling as in stampede, once a frame: it reads back `flags` (160 KB) and uploads `culledBuffer`.

**skeletons** (known culling, plus a grid chain): waits 1.8 to 9.4 ms a frame, the culling's `flags` (4.8 KB, twice a frame) and also `ranges` (6.3 KB) and `copying` (4.8 KB) once a step. The horde's machine `Doing` runs its step on the CPU (`Doing_stepping`), because a helper function writes `Pose_device`. That step finds the nearest skeleton through `cells.around` and `cells.range` (`skeletons/horde.ts`, `nearest`). The grid builds those cells on the GPU each step (`seeder`, `merger`, `copyingPipeline` and the rest, `packages/typegpu-kit/src/grid.ts`), so the step reads the grid's `ranges` and `copying` back. In run 2 that chain waited 4.9 ms a frame, more than the culling. `Doing_stepping` also writes `Pose_device` on the CPU, so GL uploads 62 KB a frame of it.

**fireworks** (known): waits 0.25 to 3.3 ms a frame, the most unstable figure here. `shells_step` runs on the CPU because the shells' `died` emits stars in a loop. The shells' `born` and `died` call `tails.reset`, so it binds the tails' `ringsBuffer` (384 B). `shellsFollowed`, a GPU form, wrote that buffer the step before with `tails.push`, so each step reads it back. Placement moved `stars_step`, `flashes_step` and `smoke_step` to the CPU in both runs. What the wait costs depends on how much GPU work is queued before the read.

**platformer** (documented, not on the known list): waits 1.35 to 1.6 ms a frame, two reads of the 4-byte `live_counts`. The coins (`platformer/coins.ts`) use `liveLists`: `live_mark` and `live_gather` run as GPU forms, and `live_finish` runs on the CPU, because it writes `live_dispatches` at indices of two shapes. Twice a frame it reads back the count that `live_gather` wrote. LIMITATIONS's "Device" section describes this wait for live lists. The coins' table is written on the CPU, so the marks the GPU computes come from rows the CPU already holds. fishtank runs the same `live_finish`, but its read costs 0.002 ms, presumably because little GPU work is queued before it.

**dominoes** (new upload): uploads 131 to 134 KB a frame, nearly all of it `Domino_device` (488 KB). `falling` runs on the CPU because `strike` emits three dust particles in a runtime loop (`for (let k = 0; k < 3; k++)` around `dust.emit`, `dominoes/topple.ts`). Placement then puts `placing`, which reads `falling`'s `motion`, on the CPU too. `placing` rewrites every live domino's row, so GL uploads `Domino_device` once a step, plus the dust's `poolBuffer`. Nothing is read back.

**jellies** (new upload): uploads 101 to 104 KB a frame of `pointBuffer` (541 KB). `trailing` integrates the strands on the CPU, because it writes `lastBuffer` at computed cells inside a loop (`jellies/swarm.ts`, `trail`). `swimming` runs there too, because it uses the workgroup variable `crowd`. The strands' drawing reads `pointBuffer`, so GL uploads what `trailing` wrote each step, 3.2 ms of CPU kernel time a frame in run 2. Nothing is read back, since both kernels run on the CPU.

Everything else waits under 0.01 ms and uploads under 8 KB a frame. quiver-trees runs its culling on the CPU, `cullFlagging` included (placed there), so it reads nothing back but spends 3.3 to 5.9 ms a frame in CPU kernels.

## What would remove the costliest new one

night-market's wait belongs to `dof`, not the example. `dof` copies the focus that `move` computes into the settings uniform, only so the passes can read `settings.focus`. If those passes read the focus from `state` itself, through a read-only accessor of that buffer, the copy and the readback would go on both backends. That changes `focus()` and `atFocus` in `packages/typegpu-kit/src/post/dof.ts`, plus its header's `@binds`. The general fix is in the device: a `copyBufferToBuffer` whose source GL holds newer, and whose destination is read only by GL, could copy on GL. It would `readPixels` the source's data texture into the destination's GL buffer through `PIXEL_PACK_BUFFER`, then mark the destination newer on GL, and nothing would wait. Any module that copies a GPU-written value into a uniform has this cost.

The grid chain in skeletons comes second. Either `Doing`'s step runs on the GPU, which needs the machine's hooks to stop writing `Pose_device` from a helper, in `machines` or `poses`. Or the grid builds its cells on the CPU on the fallback when its reader runs there, a `backends.of(root)` branch in `grid.ts` like the culling's.

## What the stats cannot tell

- How long a read waited for the GPU and how long the transfer took. Both are in one synchronous `readPixels`, so a 4-byte read can carry milliseconds of other passes' work. A fence before the read, or the time the transfer alone takes, would split them.
- Bytes of texture uploads. `upload` counts textures and milliseconds only.
- Which command caused a read. Buffer reads are keyed by label and size, not by the kernel or copy that synced them. night-market's `state` read showed up only because no CPU kernel ran that could have caused it.
- Simulation steps. Stats are per frame, and the frame rate changes how many fixed steps fall in each frame.
